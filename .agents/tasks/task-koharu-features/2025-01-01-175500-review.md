# Multi-engine translation expansion and PSD export

This change adds four features inspired by the Koharu manga translator: Claude (Anthropic) and DeepSeek as translation/OCR engines, a configurable OpenAI-compatible custom endpoint for self-hosted models, Lama Cleaner as an alternative inpainting backend, and frontend-only PSD export with editable text layers. The implementation follows the existing provider pattern throughout — each new engine gets a backend provider module, BYOK header plumbing, frontend settings modal, and pipeline integration. The scope is large (1830 lines across 35 files) but mechanically consistent.

**Watch for:** Custom OpenAI endpoint sends user-configured base URL in a header visible to any network observer (confirmed). API keys for all new providers are persisted in localStorage without encryption (confirmed, same as existing pattern). The PSD export silently swallows errors with no user feedback (confirmed). Lama Cleaner inpainting has no timeout or size guard on images sent to an arbitrary user-provided URL (likely).

## High-level view

The provider layer adds claude.py, deepseek.py, and custom_openai.py following the same httpx + retry + classify_error template as the existing openai.py. Claude is the only new engine that supports vision (OCR); DeepSeek and Custom OpenAI are translation-only.

The pipeline orchestrator (`pipeline.py`) grows routing logic for the new engines. Claude mirrors the OpenAI path — same OCR engine as translation engine means a unified pass; different engines mean separate OCR then translate. DeepSeek and Custom OpenAI slot in as translate-only backends. Lama Cleaner runs sequentially after OCR (needs bounding boxes for mask generation) and is non-fatal on failure.

The BYOK plumbing adds three new credential headers and two custom-endpoint metadata headers (`X-Custom-Base-Url`, `X-Custom-Model`). The custom endpoint pattern is novel: the user's base URL and model name travel as HTTP headers alongside the API key, making them visible in access logs and proxy layers.

The PSD export is entirely client-side using ag-psd. It loads images onto canvas elements, generates text layers positioned from bubble bounding boxes, and triggers a browser download.

<summary>Issues (5)</summary>

1. **Custom endpoint URL in cleartext header** — `X-Custom-Base-Url` carries the user's configured endpoint URL (potentially an internal network address) in an HTTP header on every pipeline request. If the backend is behind a proxy that logs headers, this leaks infrastructure topology. Consider passing it in the JSON request body instead.
2. **PSD export swallows errors silently** — `handleExportPsd` catches all exceptions and only logs to console. The user gets no toast, no visual indicator that export failed. Add a toast notification on failure.
3. **Lama Cleaner SSRF potential** — The `lama_url` value comes from a user-controlled header and is used to make an outbound HTTP POST from the backend. A malicious client could point it at internal services. Add URL validation or restrict to localhost/allowed-list.
4. **No backend tests for new providers** — Three new provider modules and significant pipeline routing logic have zero pytest coverage. Any regression in error classification or retry behavior will go unnoticed.
5. **Claude unified plan uses `ocr-only` step kind** — When Claude is both OCR and translator (same model), `planPipeline.ts` returns `{ kind: 'ocr-only', engine: 'CLAUDE' }` instead of a `unified-claude` step kind like Gemini's `unified-gemini`. The backend handles this correctly, but the frontend plan is misleading for debugging/UI display.

## Custom endpoint trust boundary

The Custom OpenAI integration passes the user's configured `base_url` from the frontend as an `X-Custom-Base-Url` HTTP header. The backend's `KeyResolver.custom_base_url()` extracts it and the pipeline makes an outbound POST to that URL. This creates two concerns:

First, the URL is a header — it appears in access logs, CDN edge logs, and any middleware that inspects headers. If the user is pointing at an internal LM Studio instance (`http://192.168.1.50:11434/v1`), that address is now exposed to every hop between browser and backend.

Second, the backend will POST to any URL the client provides. A malicious request could target `http://169.254.169.254/latest/meta-data/` or internal services. The lama_cleaner provider has the same pattern: `X-Lama-Url` becomes an outbound POST target.

```python
# backend/app/providers/custom_openai.py line 108
url = base_url.rstrip("/") + "/chat/completions"
# ...
resp = await client.post(url, json=payload, headers=headers)
```

A basic mitigation: validate that the URL scheme is `http` or `https`, reject URLs targeting RFC 1918 ranges or link-local addresses when running in production mode. For header exposure, moving these values into the JSON body (alongside `imageBase64`) removes them from log-visible transport metadata.

## Lama Cleaner sequencing and connection reuse

The inpainting step runs after OCR because it needs bounding boxes for mask generation. This means inpainting adds latency serially rather than running in parallel like the Torii cleaner — an inherent architectural trade-off given the data dependency.

The Lama Cleaner provider creates a new `httpx.AsyncClient` on each retry attempt (the `async with` is inside the for loop), so the connection pool is not reused across retries. With a 120-second timeout per attempt and up to 3 retries, a hung Lama Cleaner endpoint could block for 6 minutes before the pipeline fails gracefully.

## PSD export error handling gap

```typescript
// components/MangaViewer.tsx
const handleExportPsd = async () => {
  if (isExportingPsd) return;
  setIsExportingPsd(true);
  try {
    const blob = await exportToPsd(image);
    const filename = image.fileName.replace(/\.[^.]+$/, '') + '.psd';
    downloadBlob(blob, filename);
  } catch (err) {
    console.error('PSD export failed:', err);
  } finally {
    setIsExportingPsd(false);
  }
};
```

If `exportToPsd` throws (e.g., cross-origin image load failure, canvas tainted), the user sees the button stop pulsing and nothing else. The application already has a toast system (`useToastStore.getState().addToast()`); a one-line addition here would surface the failure visually.

The `loadImageAsCanvas` function sets `crossOrigin = 'anonymous'` on the img element. If `image.imageUrl` is ever a remote URL served without CORS headers, the canvas will be tainted and `writePsd` will produce a corrupt file with no user-facing indication.

## Frontend plan asymmetry for Claude unified mode

When Claude is used as both OCR and translator (`ocr === trans && isClaude(ocr)`), the frontend `planPipeline.ts` returns:

```typescript
steps.push({ kind: 'ocr-only', engine: ocr });
```

Compare this to the Gemini unified path which returns `{ kind: 'unified-gemini', model: ocr }`. The backend correctly treats Claude-same-model as a unified pass (sets `ocr_skip_translation=False, translation_done_in_ocr=True`), but the frontend plan displayed in `console.debug('[pipeline] plan:', plan)` will show `ocr-only` for what is actually a unified OCR+translate call. The test file asserts this behavior, so it's intentional — but if the frontend ever uses plan steps to drive UI (progress indicators, cost breakdowns), this mislabeling will cause incorrect display.

## No backend test coverage for new providers

The diff adds 3 new frontend test cases to `planPipeline.test.ts`, but no pytest tests for the backend. The new providers (claude.py, deepseek.py, custom_openai.py, lama_cleaner.py) have no unit tests. The pipeline routing changes (new `_is_claude`, `_is_deepseek`, `_is_custom_openai` branches, Lama Cleaner integration) are untested. Error classification logic — particularly the Anthropic-specific `"invalid x-api-key"` pattern — could regress without detection.
